MemoryLake 实现了 Google 的 [A2A（Agent 对 Agent）协议](https://a2a-protocol.org/)。如果您已熟悉 A2A，可以使用任何兼容 A2A 的客户端与 MemoryLake Agent 交互。

有关标准请求和响应 schema，请参阅 [A2A 规范](https://a2a-protocol.org/latest/specification/)。官方 SDK 可在 [github.com/a2aproject](https://github.com/a2aproject) 获取。

<Note>
**所需权限：** `workspace_agent:a2a`
</Note>

## Base URL

```
https://app.memorylake.cn/openapi/memorylake/api/v3/workspaces/{workspaceId}/agents/{agentId}/a2a
```

直接追加标准 A2A 路径即可 —— 例如 `POST {baseUrl}/message:send` 或 `GET {baseUrl}/tasks/{taskId}`。

## 协议版本

MemoryLake 并行暴露两套 A2A 路由，分别对应一个协议版本；每个版本都可以通过**两种传输方式**调用：REST 与 JSON-RPC 2.0。

| 协议版本 | REST 路由 | 消息体 | `role` 取值 |
|---|---|---|---|
| **A2A v1.0** | `{baseUrl}/message:send`、`{baseUrl}/tasks/...` | `message.parts`（proto-JSON，part 不带 `kind` 判别符） | `ROLE_USER` |
| **A2A v0.3** | `{baseUrl}/v1/message:send`、`{baseUrl}/v1/tasks/...` | REST：`message.content` · JSON-RPC：`message.parts`，每个 part 带 `kind` 判别符 | REST：`ROLE_USER` · JSON-RPC：`user` |

<Warning>
`/v1/` 路径前缀指的是较旧的 **A2A v0.3** 传输格式，而非协议 1.0 版本。不带前缀的路由实现的才是当前的 **A2A v1.0** 格式。请确保请求体结构与所调用的路由匹配 —— v0.3 风格的 REST 请求体（`message.content`）会被 v1.0 REST 路由拒绝，反之亦然。
</Warning>

走 JSON-RPC 时，两个协议版本都 POST 到不带后缀的 `{baseUrl}`，由 `method` 指定具体操作：v1.0 使用 `SendMessage`、`SendStreamingMessage`、`GetTask`、`CancelTask`、`SubscribeToTask`；v0.3 使用 `message/send`、`message/stream`、`tasks/get`、`tasks/cancel`、`tasks/resubscribe`。协议版本由方法名协商得出；v1.0 客户端还应额外发送 `A2A-Version: 1.0`。

四组路由都接受同一个 `configuration` 对象，以及下文描述的同一套 MemoryLake 扩展。两个协议版本对「是否等待任务完成」的开关叫法不同：

| `configuration` 字段 | 版本 | 类型 | 说明 |
|---|---|---|---|
| `returnImmediately` | v1.0 | boolean | 为 `true` 时任务一创建就返回，不等它执行完。默认 `false`，即等任务完成后再返回。v1.0 路由会忽略 `blocking`。 |
| `blocking` | v0.3 | boolean | 为 `true` 时等任务执行完成后再返回。不传时 REST 路由会立即返回，JSON-RPC 方法则会等待，所以请显式设置。 |
| `historyLength` | 两者 | integer | 响应中携带的任务历史消息条数（取最近若干条）。传 `0` 时不返回 `history`。不传时返回完整历史，但 v0.3 REST 不传时不返回 `history`。 |
| `acceptedOutputModes` | 两者 | array | 客户端可处理的输出 MIME 类型。 |

<Note>
**不支持推送通知。** Agent Card 声明 `pushNotifications: false`，传 `pushNotificationConfig`（v0.3）或 `taskPushNotificationConfig`（v1.0）都不会收到回调。要跟踪任务进度，请使用流式响应，或[订阅这个任务](#跟踪任务)。
</Note>

<Warning>
**同一会话一次只处理一条消息。** 使用相同 `contextId` 的消息属于同一个会话，同一会话同一时间只能处理一条消息。上一条消息仍在处理时（包括非阻塞发送后任务尚未结束），用同一 `contextId` 发送的新消息会被直接拒绝（`400 INVALID_ARGUMENT`），不会排队。请等上一条消息的响应或任务结束后再发送下一条；需要并行处理的请求，请为每个请求使用不同的 `contextId`。

**一个会话只对应一个 Agent。** `contextId` 归属于第一次使用它的 Agent，用同一个 `contextId` 向其他 Agent 发送的消息会被拒绝。要与另一个 Agent 对话，请使用新的 `contextId` 开启新会话。
</Warning>

## MemoryLake 扩展

MemoryLake 通过 `metadata.memorylake` 命名空间扩展了标准 A2A 协议。在 `message:send` 或 `message:stream` 请求的 `metadata` 里传入此对象：REST 请求体放在顶层 `metadata`，JSON-RPC 放在 `params.metadata`。Agent 不会从 `message.metadata` 里读取这些字段。

这是与普通 A2A 服务器的核心区别 —— 这些字段将 Agent 连接到 MemoryLake 中的工作空间、项目和 Actor。对象里的字段分两类：

- **[记忆与身份](#记忆与身份)**：`actorId`、`readWriteProjectId`、`readOnlyProjectIds`、`skipMemory`，决定 Agent 使用谁的记忆、读写哪些项目。
- **[运行配置](#运行配置)**：`overrides`、`runtimeOptions`，调整 Agent 处理这条消息的方式。

请使用本页列出的驼峰字段名。未知字段会被忽略而不是报错，所以某个设置看起来没生效时，请先检查拼写。`metadata` 下除 `memorylake` 以外的键，Agent 都不会读取。

<Note>
**`metadata.memorylake` 必须传。** 不传时请求返回 `400 INVALID_ARGUMENT`。传空对象 `{}` 即使用默认设置：Agent 使用您自己的 Actor，记忆处于开启状态。
</Note>

### 记忆与身份

<ParamField body="actorId" type="string">
发出这条消息的终端用户，填 MemoryLake 的 Actor ID（`actor-` 加 32 位十六进制字符）。Agent 会检索这个 Actor 的记忆，会话中用户一方的发言也记在这个 Actor 名下，从而实现按用户记忆。

- **默认值：** 当前认证用户在该工作空间里的 Actor。该用户在这里没有 Actor 时，请求返回 `400 STATE_NOT_READY`。
- **必须**是已绑定到该工作空间的 Actor。其他 ID 返回 `400`，已删除的 Actor 返回 `400 ACTOR_INACTIVE`。
- **权限：** 需要对该 Actor 有 `workspace_actor:fact_add` 和 `workspace_actor:fact_search`。会话开始时校验一次；之后某条消息带来会话里还没有过的 Actor 时，会再校验。
</ParamField>

<ParamField body="readWriteProjectId" type="string">
Agent 工作所在的项目（`proj-` 加 32 位十六进制字符）。Agent 会检索这个项目的文档和记忆，会话也记在这个项目下，从会话中提取的记忆就保存在这里。会话历史本身存储在工作空间层级。

- **一个会话只绑定一个项目。** 会话（`contextId`）的第一条消息绑定项目，之后的消息可以不传，沿用该项目。传入不同的项目，或者给一个开始时没有项目的会话补上项目，都会返回 `400`。
- **只能是同一工作空间的项目。** 其他工作空间的项目返回 `404`。
- **权限：** 需要对该项目有 `project:mem_add`、`project:doc_add`、`project:mem_search` 和 `project:doc_search`，在会话开始时校验。
- **带文件时必填。** 消息里的文件（`drive://` 引用或 inline 字节）会作为文档导入这个项目。带文件的消息必须自己写明项目，不能靠从会话继承，否则请求返回 `400`。
</ParamField>

<ParamField body="readOnlyProjectIds" type="string[]">
Agent 可以检索（文档和记忆）但不会写入的其他项目。用于让 Agent 访问共享知识库。

- **只对这一条消息生效。** 它不会存到会话里，所以每条需要看到这些项目的消息都要带上。
- **权限：** 需要对每个项目有 `project:mem_search` 和 `project:doc_search`，缺任何一项都返回 `403`。
- 找不到对应项目的 ID 会被跳过，不报错。
</ParamField>

<ParamField body="skipMemory" type="boolean" default="false">
为 `true` 时，这条消息不使用记忆：Agent 不检索记忆和项目文档，这条消息的内容也不会写入记忆。会话照常创建，对 Actor 和项目的权限照常校验。
</ParamField>

### 运行配置

<ParamField body="overrides" type="object">
只对这一条消息修改 Agent 的配置。没有传的项沿用 Agent 自身的配置。
<Expandable title="覆盖字段">
  <ParamField body="model" type="string">
  替代 Agent 模型的模型代码，例如 `gpt-4o`。会在您的组织可用的模型中查找。模型不存在不会让请求失败，而是任务以失败状态结束，错误信息为 `LLM model config not found: <model>`。
  </ParamField>

  <ParamField body="systemPromptOverride" type="string">
  替换这条消息中 Agent 自身的指令。MemoryLake 的内置指令（例如如何使用工具和能力、用什么语言回答）仍然生效，所以只需描述 Agent 的角色和任务。
  </ParamField>

  <ParamField body="modelParams" type="object">
  这条消息的采样参数。键名用蛇形命名，`maxTokens` 和 `topP` 也可以。
  <Expandable title="模型参数">
    <ParamField body="max_tokens" type="integer">回答的最大 token 数。</ParamField>
    <ParamField body="temperature" type="number">采样温度。</ParamField>
    <ParamField body="top_p" type="number">核采样阈值。</ParamField>
  </Expandable>
  类型不对的值会被单独丢弃，不报错，其他参数照常生效。未知的键会被忽略。MemoryLake 不检查取值范围。
  </ParamField>

  <ParamField body="capabilitiesOverride" type="object">
  为这一条消息额外开启的能力，键是能力名，值是该能力的配置。可用 `web_search`、`web_fetch`、`pii`、`vega`、`dataset`。各能力的作用，以及它与 Agent 自身配置的关系，见[按消息开启能力](#按消息开启能力)。
  </ParamField>
</Expandable>
</ParamField>

<ParamField body="runtimeOptions" type="object">
这条消息的运行选项。
<Expandable title="运行选项字段">
  <ParamField body="language" type="string">
  Agent 回答使用的语言，填语言名称，例如 `English`、`Chinese`、`Japanese`。`en` 视为 `English`，`zh` 或 `cn` 视为 `Chinese`，其他值按原样使用。不传时，Agent 用用户提问的语言回答。
  </ParamField>
</Expandable>
</ParamField>

### 按消息开启能力

`overrides.capabilitiesOverride` 用来给单条消息额外开启能力。它是一个对象：键是能力名，值是该能力的配置。能力名及其字段一律用蛇形命名（snake_case），与周围的驼峰字段不同（也接受 `webSearch`、`openDatasets` 这样的驼峰写法）。

```json
"capabilitiesOverride": {
  "web_search": { "open_datasets": ["research/academic"] },
  "web_fetch": {},
  "pii": {},
  "vega": {},
  "dataset": { "enabled_service_bundles": ["nl2sql"] }
}
```

| 能力 | 作用 | 配置 |
|---|---|---|
| `web_search` | 联网搜索。加上 `open_datasets` 后，还会检索 MemoryLake 精选的 Open Data 数据集。 | `open_datasets`（可选）：数据集标识符数组，可用值见[列出 Open Data 数据集](/features/memorylake/api-reference/a2a/list-open-data-collections)。只需联网搜索时传 `{}`。 |
| `web_fetch` | 按 URL 读取网页正文，例如用户发来一个链接请 Agent 总结。 | 无，传 `{}`。 |
| `pii` | 在消息发给模型之前遮盖个人信息：邮箱、中国大陆手机号与身份证号、银行卡号、IP 地址等会被替换成 `[EMAIL_REDACTED]` 这样的占位符。模型看不到原值，所以回答里也只有占位符；会话记录保留原文。 | 无，传 `{}`。 |
| `vega` | 生成图表：Agent 可以把数据画成柱状图、折线图、饼图、散点图等图表。 | 无，传 `{}`。 |
| `dataset` | 数据库查询：Agent 可以用自然语言查询团队里已接入的数据库，会先列出可用的库、查看表结构，再执行查询。可查询的是团队下的全部数据库，不限于本次请求的项目。数据库的接入见[数据库 API 概览](/features/memorylake/api-reference/database/overview)。 | `enabled_service_bundles`：传 `["nl2sql"]`，目前只支持这一个值。 |

使用时请注意：

- **只对这一条消息生效。** 同一会话的下一条消息不带这个覆盖，就不会开启。
- **Agent 默认没有这些能力。** 不传覆盖时，只有 Agent 自身配置了联网搜索或读取网页，它才会使用（见[创建 Agent](/features/memorylake/api-reference/agents/create-agent) 的 `capabilities`）。`pii`、`vega` 和 `dataset` 只能在这里开启。
- **传入的配置会替换 Agent 自身的配置。** 请给出该能力完整的配置，不要指望从 Agent 那里继承字段。例如 Agent 的 `web_search` 配置了 `open_datasets`，而这次只传 `"web_search": {}`，这条消息就不会检索任何 Open Data 数据集。
- **只能开启，不能关闭。** 不传某个能力，即沿用 Agent 自身的配置；传 `null` 也关不掉 Agent 已有的能力。`{"enabled": false}` 更要避免：并没有 `enabled` 这个字段，它会被当成 `{}`，反而以默认配置**开启**该能力，即使 Agent 原本没有。需要不带某个能力运行时，请使用没有配置该能力的 Agent。

<Warning>
**写错不会报错。** 拼错的能力名会被忽略。某个能力的配置不合法时（例如 `open_datasets` 传成字符串、`web_search` 传成 `true`），整个能力会被丢弃，请求照常返回 200，只是这次没有该能力。不认识的 Open Data 标识符会被跳过，全部无效时只做普通联网搜索。只有 `capabilitiesOverride` 本身不是对象（例如传成数组）时才会返回 400。如果 Agent 表现得像是没开某个能力，请先核对您请求里的能力名和配置。
</Warning>

## 示例

发送一条消息涉及三个彼此独立的选择 —— **协议版本**（v1.0 / v0.3）×**方法**（send / stream）×**传输方式**（REST / JSON-RPC），因此共有 8 种有效组合。以下把 8 种全部列出。

下表的路径均相对于上文的 base URL；JSON-RPC 一律 POST 到不带后缀的 base URL，由 `method` 指定操作。

| # | 组合 | 请求 | header |
|---|---|---|---|
| 1 | v1.0 · send · REST | `POST /message:send` | — |
| 2 | v1.0 · stream · REST | `POST /message:stream` | SSE |
| 3 | v0.3 · send · REST | `POST /v1/message:send` | — |
| 4 | v0.3 · stream · REST | `POST /v1/message:stream` | SSE |
| 5 | v1.0 · send · JSON-RPC | `SendMessage` | v1.0 |
| 6 | v1.0 · stream · JSON-RPC | `SendStreamingMessage` | v1.0 + SSE |
| 7 | v0.3 · send · JSON-RPC | `message/send` | — |
| 8 | v0.3 · stream · JSON-RPC | `message/stream` | SSE |

上表 **header** 列中，**SSE** 表示 `Accept: text/event-stream`，**v1.0** 表示 `A2A-Version: 1.0`。8 种组合都使用相同的 `configuration` 字段（v1.0 默认等待并使用 `returnImmediately`，v0.3 使用 `blocking`）和同一套 `metadata.memorylake` 扩展。其中 4 个 streaming 变体以 `text/event-stream` 返回；4 个 send 变体返回单个 JSON 响应体。

<Note>
请注意版本与传输方式之间的三处结构差异：v1.0 使用 `parts`，`role` 为 `"ROLE_USER"`；v0.3 **REST** 使用 `content`，`role` 为 `"ROLE_USER"`；v0.3 **JSON-RPC** 使用 `parts` 且每个 part 都带 `kind` 判别符，`role` 为小写的 `"user"`。
</Note>

### JSON-RPC 传输

两个协议版本共用同一个路径 —— 不带任何后缀的 `POST {baseUrl}`。协议版本由方法名决定；v1.0 客户端还应额外发送 `A2A-Version: 1.0`。

<CodeGroup>
```bash 5 · v1.0 send（JSON-RPC）
curl -X POST 'https://app.memorylake.cn/openapi/memorylake/api/v3/workspaces/ws-8001856949ad4f6a5b6226f415ffa877/agents/agent-f8bf71ab17ed8eccad8c0e8ae708273f/a2a' \
  -H 'Authorization: Bearer sk_xxxxxx' \
  -H 'Content-Type: application/json' \
  -H 'A2A-Version: 1.0' \
  -d '{
    "jsonrpc": "2.0",
    "id": "req-1",
    "method": "SendMessage",
    "params": {
      "message": {
        "messageId": "msg-1",
        "role": "ROLE_USER",
        "parts": [
          { "text": "How do I configure two-factor authentication?" }
        ],
        "contextId": "ctx_m4n7p2q9"
      },
      "configuration": {
        "returnImmediately": false,
        "historyLength": 10
      },
      "metadata": {
        "memorylake": {
          "actorId": "actor-33d6b73298fb43482a765643ff92444b",
          "readWriteProjectId": "proj-b93e8d95a8705bcc4ec42a65ba4cc7f8",
```

## 响应

所有组合返回的都是同一套任务模型，只有外层结构和少数拼写随协议版本和传输方式变化，见 [v0.3 的差异](#v0-3-的差异)。本节示例使用 v1.0 REST。

| 组合 | `message:send` 响应体 | `message:stream` 的每个事件 |
|---|---|---|
| v1.0 · REST | `{"task": {...}}` | `{"task": {...}}`、`{"statusUpdate": {...}}` 或 `{"artifactUpdate": {...}}` |
| v1.0 · JSON-RPC | `{"jsonrpc": "2.0", "id": ..., "result": {"task": {...}}}` | `{"jsonrpc": "2.0", "id": ..., "result": {"statusUpdate": {...}}}` 等 |
| v0.3 · REST | `{"task": {...}}` | `{"statusUpdate": {...}}` 等 |
| v0.3 · JSON-RPC | `{"jsonrpc": "2.0", "id": ..., "result": {"kind": "task", ...}}` | `{"jsonrpc": "2.0", "id": ..., "result": {"kind": "status-update", ...}}` 等 |

### 非流式发送

`message:send` 总是返回一个任务，不会只返回一条消息。默认会等任务执行完再返回：

```json
{
  "task": {
    "id": "run-e21fffe8d53647f4bc918bb4a8fb7d73",
    "contextId": "ctx-demo-1",
    "status": { "state": "TASK_STATE_COMPLETED" },
    "artifacts": [
      {
        "artifactId": "result-run-e21fffe8d53647f4bc918bb4a8fb7d73",
        "name": "result",
        "parts": [{ "text": "Paris is the capital of France." }],
        "metadata": {}
      }
    ],
    "history": [
      {
        "messageId": "msg-1",
        "contextId": "ctx-demo-1",
        "taskId": "run-e21fffe8d53647f4bc918bb4a8fb7d73",
        "role": "ROLE_USER",
        "parts": [{ "text": "What is the capital of France?" }]
      },
      {
        "messageId": "run-e21fffe8d53647f4bc918bb4a8fb7d73-3",
        "contextId": "ctx-demo-1",
        "taskId": "run-e21fffe8d53647f4bc918bb4a8fb7d73",
        "role": "ROLE_AGENT",
        "parts": [{ "text": "Paris is the capital of France." }]
      }

```

<ResponseField name="id" type="string">
任务 ID。
</ResponseField>

<ResponseField name="contextId" type="string">
任务所属的会话。下一条消息把它作为 `message.contextId` 传入即可继续这个会话。请求里没有传时，会生成一个新的。
</ResponseField>

<ResponseField name="status" type="object">
<Expandable title="状态字段">

  </ResponseField>

### 流式发送

`message:stream` 以 `text/event-stream` 返回，每行 `data:` 是一个 JSON 事件，顺序如下：

1. **`task`**：刚创建的任务，`history` 里是您发出的消息。
2. **`statusUpdate`**，状态 `TASK_STATE_WORKING`：Agent 开始执行。
3. **`statusUpdate`**，状态 `TASK_STATE_WORKING`：每一步进展一个，`status.message` 里只有一个 part，可能是：
   - 一段回答文字。文字是**增量**下发的，需要依次拼接；每段都有自己的 `messageId`；
   - 一段思考内容，带 `metadata.adk_thought: true`；
   - 一次[工具调用或工具结果](#工具调用)；
   - Agent 生成的文件，形如 `{"url": "...", "mediaType": "...", "filename": "..."}`。
4. **`artifactUpdate`**：回答，见[回答内容](#回答内容)。
5. **`statusUpdate`**：最终状态，`TASK_STATE_COMPLETED`、`TASK_STATE_FAILED`（`status.message` 里是错误说明）或 `TASK_STATE_CANCELED`。之后流结束。

文字片段只用于实时展示，最终回答请以 artifact 为准：片段里还包含 Agent 在调用工具前写的过渡文字，artifact 里的文字才是完整的最终回答。以 `:` 开头的行是保活注释，忽略即可。

```text
data: {"task": {"id": "run-7828…6073", "contextId": "ctx-demo-1", "status": {"state": "TASK_STATE_SUBMITTED"}, "history": [{"messageId": "msg-1", "role": "ROLE_USER", "parts": [{"text": "What is the capital of France?"}], …}]}}

data: {"statusUpdate": {"taskId": "run-7828…6073", "contextId": "ctx-demo-1", "status": {"state": "TASK_STATE_WORKING"}}}

data: {"statusUpdate": {"taskId": "run-7828…6073", "contextId": "ctx-demo-1", "status": {"state": "TASK_STATE_WORKING", "message": {"messageId": "run-7828…6073-3", "role": "ROLE_AGENT", "parts": [{"text": "Let me look that up."}], …}}}}

data: {"statusUpdate": {…, "status": {"state": "TASK_STATE_WORKING", "message": {"messageId": "run-7828…6073-8-call", "role": "ROLE_AGENT", "parts": [{"data": {"id": "call_1", "name": "web_search", "args": {"query": "capital of France"}}, "metadata": {"adk_type": "function_call"}}], …}}}}

data: {"statusUpdate": {…, "status": {"state": "TASK_STATE_WORKING", "message": {"messageId": "run-7828…6073-9-response", "role": "ROLE_AGENT", "parts": [{"data": {"id": "call_1", "name": "web_search", "response": "{\"results\": [{\"title\": \"Paris\", \"url\": \"https://en.wikipedia.org/wiki/Paris\"}]}"}, "metadata": {"adk_type": "function_response"}}], …}}}}

data: {"artifactUpdate": {"taskId": "run-7828…6073", "contextId": "ctx-demo-1", "artifact": {"artifactId": "result-run-7828…6073", "name": "result", "parts": [{"text": "Paris is the capital of France."}, {"data": {"kind": "recommended_questions", "questions": ["What is the population of Paris?"]}}], "metadata": {}}, "lastChunk": true}}
```

### 回答内容

名为 `result` 的 artifact 以一组 part 承载回答：

| Part | 形式 | 说明 |
|---|---|---|
| 回答文字 | `{"text": "..."}` | 最终回答。 |
| 附件 | `{"data": {"kind": "attachments", "attachments": [...]}}` | Agent 生成的文件。每项包含 `name`、`mime_type`、`presign_url`（下载链接）和 `description`；文件保存失败时 `committed` 为 `false`，`error` 说明原因。 |
| 推荐追问 | `{"data": {"kind": "recommended_questions", "questions": ["..."]}}` | 用户接下来可能想问的问题。只在 Agent 给出推荐时出现。 |

artifact 和流里还可能出现其他 `data` part。遇到不认识的 `kind`，或者没有 `kind` 的 `data` part，跳过即可。`data` part 里的数字会以浮点数返回，例如 `2` 会变成 `2.0`。

### 工具调用

Agent 的工具调用以 `data` part 的形式出现，用 `metadata.adk_type` 标记，这是 Google Agent Development Kit 的约定。流和 `history` 里都会出现。

| `metadata.adk_type` | `data` | 说明 |
|---|---|---|
| `function_call` | `{"id", "name", "args"}` | Agent 调用工具时、工具实际运行前发出。`args` 是对象。 |
| `function_response` | `{"id", "name", "response"}` | 工具结果，`id` 与对应的调用一致。`response` 通常是 JSON 编码后的字符串；工具出错时为 `{"error": "..."}`，有错误码时还会带 `code`。 |

工具调用上可能还带有 `metadata.adk_thought_signature`，这是一个不透明的值，忽略即可。

### 跟踪任务

`GET {baseUrl}/tasks/{taskId}`（v0.3：`{baseUrl}/v1/tasks/{taskId}`）只返回任务的 `id`、`contextId` 和 `status`（含 `state` 与 `timestamp`）：不包含回答和历史，失败的任务也不带错误说明。

要拿到一个没有等待的任务的回答，请订阅它：`GET {baseUrl}/tasks/{taskId}:subscribe`（v0.3：`{baseUrl}/v1/tasks/{taskId}:subscribe`），并带上 `Accept: text/event-stream`。它会从头重放该任务的事件，格式与 `message:stream` 相同，只是开头没有 `task` 事件；之后实时跟随，直到任务结束。已经失败或被取消的任务无法订阅。

### 错误

**任务失败。** 请求仍然返回 HTTP 200，任务以 `TASK_STATE_FAILED` 结束，`status.message.parts[0].text` 是错误说明。例如 `overrides.model` 填了不存在的模型时，任务失败，错误为 `LLM model config not found: <model>`。

**请求被拒绝。** REST 路由返回 HTTP 错误状态码和标准的[错误响应体](/features/memorylake/api-reference/errors)（`success`、`message`、`error_code`），例如：

| 状态码 | `error_code` | 场景 |
|---|---|---|
| 400 | `INVALID_ARGUMENT` | 请求不合法，或同一会话里还有消息正在处理。 |
| 402 | `QUOTA_EXCEEDED` | 配额已用完。 |
| 403 | `ACCESS_DENIED` | 缺少请求所需的权限。 |
| 404 | `NOT_FOUND` | Agent 或任务不存在。 |

JSON-RPC 下，MemoryLake 在 Agent 运行之前发现的错误（例如配额或权限错误）同样使用上面的 HTTP 状态码和错误响应体；Agent 报告的错误则以 JSON-RPC `error` 对象返回，HTTP 状态码为 200，其中 v0.3 方法一律使用错误码 `-32603`。

### v0.3 的差异

- **JSON-RPC。** result 直接就是任务，带 `"kind": "task"`。流事件带 `"kind": "status-update"` 或 `"artifact-update"`，最后一个状态更新带 `"final": true`。状态用小写，例如 `completed`、`failed`、`canceled`、`submitted`、`working`；角色为 `user` 和 `agent`。每个 part 都带 `kind`：`{"kind": "text", "text": ...}`、`{"kind": "data", "data": {...}}` 或 `{"kind": "file", "file": {...}}`。
- **REST。** 状态拼写与 v1.0 相同，只有已取消拼作 `TASK_STATE_CANCELLED`。消息的 part 放在 `content` 下而不是 `parts`，data part 的形式是 `{"data": {"data": {...}}}`。`GET` 返回的任务不带 `timestamp`。
- **REST 的默认值。** 不传 `blocking` 时，`message:send` 会立即返回而不是等待；不传 `historyLength` 时不返回 `history`。请显式设置这两个字段。
